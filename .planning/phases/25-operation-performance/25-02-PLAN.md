<objective>
Replace the sequential per-card `await` loops in both bulk operation routes with single-round-trip batch Drizzle queries, eliminating Vercel function timeouts for collections up to 1,000 cards.

Purpose: PERF-04's core requirement is that Quick Add and CSV Import complete without timeout for 1,000-card collections. The root cause of timeouts is the existing N + M sequential Neon HTTP round-trips. The fix is architectural: replace N + M round-trips with 1 + 1 round-trips via Drizzle's multi-row `.values([...])` + `inArray` SELECT GROUP BY.

Output: Three new exported batch helpers in `collection.ts` (preserving additive vs overwrite semantics distinction per D-01/D-02/D-03), both route handlers refactored to call the batch helpers exactly twice each, all existing tests pass, Wave 0 stubs converted to real GREEN tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → API (POST /api/collection/import) | Untrusted JSON array of swudbId/variantType/count rows |
| client → API (POST /api/collection/starter-deck) | Untrusted deckId string |
| API → DB (batch INSERT/SELECT) | Server-controlled inputs (userId from session; cardDefinitionIds from DB lookup; cardPrintingIds from DB lookup) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25-02-01 | Tampering | userId in batch helpers | mitigate | userId in route handlers is always `Number(session.user.id)` from `auth.api.getSession()` — never from request body; batch helpers accept userId as their second parameter from this same source |
| T-25-02-02 | Denial of Service | Oversized batch (DoS via huge import) | mitigate | `MAX_IMPORT_ITEMS = 2000` enforced before batch helper is called in import route; starter-deck route is bounded by the static `starterDecks` data (no deck exceeds ~70 cards) |
| T-25-02-03 | Tampering | SQL injection via cardDefinitionIds | mitigate | `inArray(cardPrintings.cardDefinitionId, cardDefinitionIds)` uses Drizzle parameterization — never `sql.raw`; cardDefinitionIds always come from a DB lookup keyed by user-provided values, not directly from client input |
| T-25-02-04 | Tampering | cardPrintingId tampering via mapping | mitigate | `mapping` is built from a DB query (`db.select().from(cardPrintings).innerJoin(cardDefinitions)`) — the printing IDs in batch items always come from a verified DB row, not from the client payload |
| T-25-02-05 | Repudiation | Bulk write attribution | accept | Batch helpers preserve `userId` filter on every conflict target — no cross-user data contamination possible; `updatedAt: new Date()` provides audit timestamp |
| T-25-02-06 | Information Disclosure | Batch SELECT in recomputeTotals exposing other users' data | mitigate | Step 1 SELECT filters by `eq(userPrintingCollections.userId, userId)` — the SUM only aggregates the calling user's rows |
</threat_model>

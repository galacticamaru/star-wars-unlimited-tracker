<objective>
Close the one verified gap in Phase 32 (see 32-VERIFICATION.md): BINDER-19's "restore a previously excluded auto-want, behaviour preserved from before the redesign" only PARTIALLY holds. `autoWants` (only cards with a live deck shortfall > 0) and the `exclusions` array (every `tradeExclusions` row) are independent DB queries that can diverge. When an excluded card drops out of `autoWants` — its deck is deleted, or enough copies are acquired so shortfall resolves — the exclusion persists server-side but renders NOWHERE in the new two-section list, because restore is only reachable from an excluded row inside Deck Wants. Before this phase, the standalone Exclusions section rendered the full `exclusions` array, so every exclusion was restorable. This is a verified functional regression (corroborated by 32-REVIEW.md WR-01).

Fix direction (user chose "plan a gap-closure fix", NOT "accept the regression"): restore full manageability of exclusions WITHOUT reintroducing a separate Exclusions section (honor locked decision D-01). Re-thread the full `exclusions` array into `ManageWantsList` and render the "orphaned" subset (exclusions with no matching `autoWants` entry) as additional dimmed rows at the bottom of Deck Wants, each with the same restore control. This also re-activates the currently-dead `tradeData.exclusions` client state (closes REVIEW IN-01), and the same change fixes the cosmetic count/empty-state mismatch (REVIEW IN-02).

Purpose: make BINDER-19 fully true — every exclusion is restorable through the UI again — while preserving BINDER-18 (two sections, no standalone Exclusions) and BINDER-20 (manual stepper/remove unchanged).
Output: a client-side presentation change to two files. No server/API/schema change.
</objective>

Purpose: 34-01 and 34-02 built the data — `setsTotal`, `setsProcessed`, `failedSets`, `unprocessedSets` for both halves. SYNC-03 needs the caller to read it, not new plumbing.
Output: an honest cron entrypoint and the test cases that pin it.

  <action>
Add `export const maxDuration = <the CONFIRMED_MAX_DURATION_SECONDS value from 34-BUDGET.md>` at module scope, as a plain numeric literal so Next.js's static analysis of route segment config can read it. Do not import the number from another module and do not compute it — the config export must be statically analysable.

Add `const SOFT_DEADLINE_RATIO = 0.8` at module scope and, inside the handler, compute `const deadlineAt = startTime + maxDuration * 1000 * SOFT_DEADLINE_RATIO`. Deriving the deadline from the `maxDuration` export in the same file is what keeps D-08's threshold and D-09's budget from drifting apart — there is one number, and 80% of it.

Leave the auth guard at `:6-14` completely untouched, including the `!cronSecret` check ordering.

Inside the `try`, fetch the set list exactly once with `await getNonTokenSets()` and pass the same array into both halves: `syncAllCards({ sets, deadlineAt })` then `syncPrices({ sets, deadlineAt })`. One fetch, one list, both consumers — this is what makes it structurally impossible for the price half to price a different set of sets than the card half ever synced, which is the D-10 defect at the routing level.

Keep `revalidateTag('cards', 'max')` firing after both syncs and before the response is built, on the success and shortfall paths alike. Do not move it inside a conditional gated on the verdict. The sets that did land genuinely changed their data, and suppressing invalidation would serve stale cache for real updates; the failure signal belongs in the response and the freshness route, not in withheld cache invalidation.

Compute the verdict as three plain comparisons and nothing else:
`const cardsOk = cardResult.setsTotal > 0 && cardResult.setsProcessed === cardResult.setsTotal;`
`const pricesOk = priceResult.setsTotal > 0 && priceResult.setsProcessed === priceResult.setsTotal;`
`const success = cardsOk && pricesOk;`
The `setsTotal > 0` term is required by the empty-set-list case: an upstream `/sets` response that yields no non-token sets means the run learned nothing and synced nothing, and zero-of-zero must not evaluate as a complete sync. There is no threshold, no percentage, and no "mostly succeeded" allowance anywhere — a shortfall of one set is a failed run, which is exactly what D-05 locked.

Return `Response.json({ success, cards: cardResult, prices: priceResult, deadlineHit: cardResult.deadlineHit || priceResult.deadlineHit, duration: \`${duration}s\` }, { status: success ? 200 : 500 })`. Because `CardSyncResult` and `PriceSyncResult` already carry `setsTotal`, `setsProcessed`, `failedSets` and `unprocessedSets`, the body names which half fell short and which specific set codes did not land, with no extra assembly.

Before returning a non-2xx, emit one `console.error` naming the shortfall — which half, the processed-versus-total counts, and the failed and unprocessed set codes. Vercel does not notify on a cron non-2xx on Hobby, so the log and the SYNC-04 status route are the operator's only channels; a 500 with no log line is a failure nobody can diagnose.

Leave the outer catch at `:36-39` exactly as it is: `console.error('Sync failed:', error)` and `new Response('Sync failed', { status: 500 })`. Do not widen it to include the caught error object in the response body.
  </action>

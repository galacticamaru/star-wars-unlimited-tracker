<objective>
Bring the price half of the nightly run up to the same standard as the card half: one source for the set list, batched writes, no invented rate-limit sleep, and a failure count that reaches the caller instead of dying in a `console.error`.

Purpose: `prices.ts` carries three separate instances of the phase's governing defect — a hand-maintained set list that drifted (ASH/LOF/TS26 have never had a price synced), a per-card round-trip loop, and a per-set catch that makes a total failure look identical to a total success. D-07 makes prices count toward the run verdict, which is impossible until this function reports a total.
Output: a batched, deadline-aware `syncPrices()` returning `PriceSyncResult`, plus unit coverage for the set-list source, the empty-payload case, and the failure total.
</objective>

Give `syncPrices()` an optional `{ sets?: SWUSet[]; deadlineAt?: number }` parameter matching 34-01's `SyncRunOptions`. Export `PriceSyncResult` as `{ setsTotal, setsProcessed, totalUpdated, failedSets: string[], unprocessedSets: string[], deadlineHit: boolean, sets: Array<{ setCode: string; updated: number }> }`. Keep the existing per-set summary array under `sets` so `scripts/sync-prices-now.ts` output stays meaningful. `setsTotal` is the length of the iterated list; `setsProcessed` increments only when a set completes its fetch and its writes without throwing.

Keep the per-set `try`/`catch` — a bad set must not abort the run, exactly as D-05 rules for cards — but the catch must now push `setCode` onto `failedSets` in addition to its `console.error`. The error must not be re-thrown and must not be swallowed silently.

At the top of the per-set loop, before the price fetch, apply the same D-08 boundary check `syncAllCards()` uses: when `deadlineAt` is set and `Date.now() >= deadlineAt`, push every remaining set code onto `unprocessedSets`, set `deadlineHit`, and break. Reports and stops — no resume cursor, no persisted checkpoint.

Remove the hardcoded one-second inter-set delay at `:96-100` and its console line. Its own comment concedes the limit is a guess, and the sibling card loop hits the same host with no delay. Do not replace it with a retry, a backoff, or 429 handling — all explicitly deferred.

  </read_first>

  <action>
Inside each set's block, build the update rows in memory first: filter to `card.VariantType === 'Normal'` exactly as today, map through the unchanged `mapPriceData()`, and collect `{ swudbId, priceEur, priceUsd }` where `swudbId` is `` `${card.Set}-${card.Number}` ``. De-duplicate by `swudbId`, last-write-wins, so a duplicated upstream row cannot produce two conflicting CASE branches for the same key.

Add a module-local `buildCaseUpdate(rows, valueKey)` helper that returns a Drizzle `SQL` fragment of the form `(case when <cardDefinitions.swudbId> = <bound swudbId> then <bound value> ... end)`, assembled with `sql.join(fragments, sql.raw(' '))`. The separator argument must be `sql.raw(' ')`, not a plain string — `sql.join` requires a `SQL` fragment there. Every swu-db-derived value must be interpolated through the `` sql`` `` template so Drizzle binds it as a parameter; `sql.raw()` is used only for the literal separator and the fixed `case` / `end` keywords, never for API data. Letting Postgres infer each branch's type from the target column is why this shape is used instead of a hand-rolled VALUES list, whose nullable `price_eur` / `price_usd` columns would need explicit casts.

Replace the per-card loop with `for (const priceChunk of chunk(rows, SYNC_CHUNK_SIZE))`. Guard each chunk with an early `continue` when its length is 0. Per chunk, issue one `db.update(cardDefinitions).set({ priceEur: buildCaseUpdate(priceChunk, 'priceEur'), priceUsd: buildCaseUpdate(priceChunk, 'priceUsd'), pricesUpdatedAt: sql\`now()\` }).where(inArray(cardDefinitions.swudbId, priceChunk.map(r => r.swudbId)))`. Count updated rows from `.returning({ id: cardDefinitions.id })` length per chunk so `setUpdated` still reflects rows that actually exist in `card_definitions`, rather than assuming `priceChunk.length`.

Add tests: a 501-row Normal-variant payload produces exactly 2 update calls with `inArray` id-list lengths 500 and 1; a 500-row payload produces exactly 1; a payload containing zero `Normal` variants (all Foil/Hyperspace) produces 0 update calls, counts the set as processed, and does not throw; an empty card array produces 0 update calls and counts the set as processed.
  </action>

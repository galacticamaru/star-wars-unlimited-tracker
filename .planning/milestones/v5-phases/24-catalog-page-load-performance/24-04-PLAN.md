<objective>
Enable Next.js 16 RSC caching for the catalog data layer (PERF-02): wrap the three DB query functions with the `'use cache'` directive + `cacheTag('cards')`, remove `force-dynamic` from the catalog page, remove userId/collectionCount from `getAllCards`, update the two remaining call sites, and call `revalidateTag('cards', 'max')` after the daily sync.

Purpose: Per the LCP measurement, the catalog page currently re-queries Postgres on every visitor request because `force-dynamic` opts out of all caching. Card data changes only once per day (cron-driven sync). Caching the three DB query results at the RSC layer with a tag-based invalidation strategy means subsequent visitors get cached HTML and data without a DB round-trip — measurably faster LCP. Per AGENTS.md and the research, Next.js 16 replaces `unstable_cache` with the `'use cache'` directive; this plan uses the current API exclusively.

Output: `next.config.ts` enables `cacheComponents: true`; `catalog.ts` has three cached query functions; `cards/page.tsx` is session-free and call-site-clean; `decks/[id]/page.tsx` keeps its session read but calls `getAllCards()` with no argument; cron route invalidates the cache on successful sync; the build passes.
</objective>

<!-- Next.js 16 cache APIs (canonical: node_modules/next/dist/docs/) -->

`'use cache'` directive:
- Placed as the very first statement inside an async function body (after the function signature, before any await)
- Caches the function's return value across requests
- Requires `cacheComponents: true` in next.config.ts
- Source: node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-cache.md

`cacheTag(tag)`:
- Imported from `'next/cache'`
- Called INSIDE a 'use cache' scope, BEFORE any await
- Assigns a string tag for on-demand invalidation
- Source: node_modules/next/dist/docs/01-app/03-api-reference/04-functions/cacheTag.md

`cacheLife(profile)`:
- Imported from `'next/cache'`
- Optional; sets cache lifetime profile (e.g., 'days', 'hours', 'minutes', 'max')
- This phase uses `'days'` — daily sync is the dominant invalidation event
- Source: node_modules/next/dist/docs/01-app/03-api-reference/04-functions/cacheLife.md

`revalidateTag(tag, profile)`:
- Imported from `'next/cache'`
- Two-argument form is current; single-argument is DEPRECATED in Next.js 16
- Use `revalidateTag('cards', 'max')` for stale-while-revalidate semantics
- Source: node_modules/next/dist/docs/01-app/03-api-reference/04-functions/revalidateTag.md

`cacheComponents: true`:
- Set in next.config.ts NextConfig object
- Enables 'use cache' directive site-wide
- Side effect (per RESEARCH.md Pitfall 6): GET Route Handlers follow the same prerendering model as pages. `force-dynamic` exports should opt them out — verify by running build.
- Source: node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/cacheComponents.md

Constraints (per RESEARCH.md Common Pitfalls):
- Pitfall 1: `'use cache'` cannot read runtime APIs (`headers()`, `cookies()`, `auth.api.getSession()`) — they throw. After D-07, getAllCards no longer needs any of these.
- Pitfall 3: removing the LEFT JOIN to userCollections AND removing the `collectionCount: sql<number>...` SELECT column AND removing `userCollections` from the `@/db/schema` import must happen atomically. Forgetting any one of these three breaks the query.

Call sites of getAllCards (verified via grep — RESEARCH.md Breaking Callers section):
1. `src/app/cards/page.tsx` — currently `getAllCards(session?.user.id ? Number(session.user.id) : undefined)` → becomes `getAllCards()`

3. `src/app/api/cards/all/route.ts` — already calls `getAllCards()` with no arg → no change

`drizzle-orm` imports in catalog.ts currently include `sql` — `sql` is used ONLY for the `collectionCount: sql<number>\`COALESCE(...)\`` expression. Once that column is removed, `sql` can be removed from the import. Verify by searching for other `sql\`` template-literal usages in the file before removing.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| cron→cache | Cron route handler invalidates the cards cache via `revalidateTag('cards', 'max')` — protected by `CRON_SECRET` already |
| RSC→DB | `'use cache'`-wrapped query functions serve cached results to all visitors; cache keys derive only from function arguments (none) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-24-09 | Tampering | revalidateTag invocation in cron route | mitigate | Existing `CRON_SECRET` Bearer auth (lines 12–14 of route.ts) gates access. Only the authenticated cron job can trigger invalidation. |
| T-24-10 | Information Disclosure | Cached card data | accept | All three query functions return user-agnostic data: card definitions, printings, filter options. The previous `getAllCards(userId)` LEFT JOIN to `userCollections` could have leaked one user's collection counts to another user's cache — D-07 REMOVES this risk by dropping the userId parameter and join entirely. Cache poisoning surface = none. |
| T-24-11 | Denial of Service | Cache stampede on initial deploy | accept | First visitor after deploy triggers a single DB query that fills the cache. Subsequent visitors serve from cache. Standard SWR semantics via `cacheLife('days')` + `revalidateTag('cards', 'max')`. |
| T-24-12 | Elevation of Privilege | Session-free cards/page.tsx | mitigate | The catalog page never granted any user-specific privileges — it always showed the public card catalog.

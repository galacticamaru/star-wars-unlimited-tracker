## Summary

Four files were reviewed covering the new in-memory variant-grouping upsert logic (`upsertCards`), its UI consumer (`CardGrid`/`CardItem`), and two diagnostic scripts. The core variant-grouping algorithm is sound and correctly replaces the old two-pass bug. One critical correctness defect was found: the orphan-check query in `orphan-check.ts` contains a logical flaw that causes it to silently under-report actual orphans, producing false confidence in the data-repair outcome. Four warnings cover an unused import, a fragile cross-set card-name collision, a missing process-exit in `check-dup-defs.ts`, and a token-set regex discrepancy between `upsertCards` and `syncAllCards`. Two info items cover dead imports and a React key stability concern.

## Critical Issues

### CR-01: Orphan-check query does not scope by `card_definition_id` name — can produce false zeros

**File:** `scripts/orphan-check.ts:13-28` (and duplicated at lines 48-65)

**Issue:** The "orphaned variant" definition used by the query is:

> a printing that has *no Normal sibling sharing its `card_definition_id`* AND *some other Normal printing in the same `set_code` exists under a different `collector_number`*.

The second EXISTS clause (`cp3`) joins only on `set_code` and `variant_type = 'Normal'` — it does **not** constrain by the card's name or `card_definition_id`. This means:

1. Any set that contains *at least one* Normal-variant printing will cause every non-Normal printing that lacks a co-linked Normal to look orphaned — even legitimately standalone printings (e.g., a Hyperspace-only promo set).
2. Conversely, if a set contains exactly one card (one Normal, one Foil, and the Foil is pointing at the wrong definition), the query *could* still pass if the Normal's `collector_number` happens to equal the Foil's `collector_number` — the `!=` guard is the only thing preventing a self-match, but since Foil and Normal have distinct collector numbers by convention this is not protective.

More concretely: the query's intent is to find Foil/Hyperspace rows linked to the wrong definition. The correct second condition should verify that a Normal printing exists under the **same logical card** (i.e., matching `card_definition_id` via a sub-join through `card_definitions.name + subtitle`) but is instead linked elsewhere. Without that constraint the query is not a reliable orphan detector — it produces noise (false positives) and can miss real orphans (false negatives) depending on set composition.

The UAT report in phase 17-10 relied on this script returning `0` as proof of a clean re-seed. If the query is wrong, that proof is invalid.

**Fix:**
```sql
-- Correct orphan definition:
-- A card_printing is orphaned if its card_definition_id does NOT match
-- the card_definition whose swudb_id is the Normal collector number for
-- the same (name, subtitle, set_code) group.
SELECT COUNT(*)::int AS orphaned_variants
FROM card_printings cp
JOIN card_definitions cd ON cd.id = cp.card_definition_id
WHERE cp.variant_type != 'Normal'
  AND EXISTS (
    -- There is a Normal printing for the same logical card in this set
    SELECT 1
    FROM card_printings cp_normal
    JOIN card_definitions cd_normal
      ON cd_normal.id = cp_normal.card_definition_id
    WHERE cp_normal.set_code = cp.set_code
      AND cp_normal.variant_type = 'Normal'
      AND cd_normal.name     = cd.name
      AND (cd_normal.subtitle IS NOT DISTINCT FROM cd.subtitle)
      -- but it points at a DIFFERENT card_definition — that is the orphan
      AND cp_normal.card_definition_id != cp.card_definition_id
  )
```

## Warnings

### WR-01: Unused imports (`eq`, `and`, `isNull`) — leftover from old two-pass code

**File:** `src/lib/sync/upsert-cards.ts:3`

**Issue:** `eq`, `and`, and `isNull` are imported from `drizzle-orm` but are not referenced anywhere in the file. These are imports that belonged to the old two-pass SELECT-based lookup that was removed when in-memory grouping was introduced. In TypeScript strict mode they will not cause a compile error, but they are dead symbols that mislead readers into thinking a SELECT query still exists somewhere in the upsert path.

**Fix:**
```typescript
// Before
import { sql, eq, and, isNull } from 'drizzle-orm';

// After
import { sql } from 'drizzle-orm';
```

### WR-02: Token-set regex is duplicated and the two copies are not kept in sync

**File:** `src/lib/sync/upsert-cards.ts:62` and `:195`

**Issue:** The token-set guard appears in two places — once at the top of `upsertCards` (line 62) and once in the pre-filter inside `syncAllCards` (line 195). The comment on line 192–194 acknowledges the duplication and calls `upsertCards` "the canonical location." However, if the regex ever needs to change (e.g. new token set naming convention), it must be updated in both places. This has already been a maintenance hazard: the current regex `/^TS\d{2}$/` allows sets like `TS26` to pass, but there is no guard for a hypothetical `TS` set with a non-`\d{2}` suffix. The current two-copy situation also violates the single-source-of-truth principle stated in the comment.

**Fix:** Extract the predicate into a shared named function and call it from both sites:
```typescript
/** Returns true if the set should be excluded from sync (token sets, etc.) */
function isTokenSet(setId: string): boolean {
  return setId.startsWith('T') && setId.length > 3 && !setId.match(/^TS\d{2}$/);
}

// upsertCards
if (isTokenSet(setId)) return 0;

// syncAllCards
const nonTokenSets = sets.filter((s) => !isTokenSet(s.setId));
```

### WR-03: `check-dup-defs.ts` has no `process.exit` on error path — Node process may hang

**File:** `scripts/check-dup-defs.ts:30`

**Issue:** The script ends with:
```typescript
main().then(() => process.exit(0)).catch(e => { console.error(e); process.exit(1); });
```
The `catch` branch correctly calls `process.exit(1)`. However the `.then(() => process.exit(0))` is chained before the `.catch`, meaning an error thrown inside `main()` that is caught by `.catch` will still attempt to resolve `.then` before reaching `.catch` (since `.catch` is chained on the Promise returned by `.then`, not on the original `main()` Promise). In practice the database driver will likely keep open handles after a query error, so the process will **hang indefinitely** if an exception is thrown after a partial query — the `catch` branch is not reached because `.then` throws internally and its returned rejected Promise has no further `.catch`.

The correct pattern used in `orphan-check.ts` (lines 74–77) is:
```typescript
main().catch((err) => {
  console.error('check-dup-defs failed:', err);
  process.exit(1);
});
```

**Fix:**
```typescript
// Replace the final line of check-dup-defs.ts:
main().catch((e) => { console.error(e); process.exit(1); });
// (process.exit(0) is unnecessary — Node exits when the event loop drains)
```

### WR-04: In-memory grouping key collides for cards with the same name+subtitle across different `set_code` values when `upsertCards` is called with mixed-set card arrays

**File:** `src/lib/sync/upsert-cards.ts:70-78`

**Issue:** The grouping key is `"Name|Subtitle"` with no set-code component. The function currently receives a per-set `cards` array and `setId` parameter, so in practice all cards in a single call belong to one set. However, nothing in the function signature or Map logic prevents a future caller from passing a multi-set card array (e.g., reprints research, cross-set dump). If that ever happens, two cards from different sets that share a name and subtitle (e.g., reprints like "Luke Skywalker | Faithful Friend" appearing in both SOR and a hypothetical reprint set) would be merged into one group. The anchor selection would pick *one* set's collector number as `swudbId`, and all variant printings — including those from the other set — would be upserted under the same `card_definition`, creating silent data corruption.

The fix requires either (a) scoping the grouping key by set, or (b) adding an assertion that all cards in the input array share the same `Set` field, or (c) a doc comment explicitly stating the function must only be called with a single-set array.

**Fix (defensive assertion):**
```typescript
// After the nonTokenCards filter, add:
const uniqueSets = new Set(nonTokenCards.map(c => c.Set));
if (uniqueSets.size > 1) {
  throw new Error(
    `upsertCards received cards from multiple sets: ${[...uniqueSets].join(', ')}. ` +
    'Call once per set.'
  );
}
```

## Info

### IN-01: `card-grid.tsx` React key includes `mode` but not `card.id` — keys can collide when same `collectorNumber` appears in two modes on the same page

**File:** `src/components/catalog/card-grid.tsx:32`

**Issue:** The `key` prop is `\`${card.collectorNumber}-${mode}\``. If two `CardGrid` components with the same `mode` are mounted under the same parent (unlikely but possible in tests or future composable UIs), cards sharing the same `collectorNumber` will have duplicate keys. More commonly, `collectorNumber` is unique within a set but `CardForFilter` records coming from joined queries might contain printings (Foil + Normal) with different `card.id` values but when deduplicated may not always be guaranteed unique. Using `card.id` (the primary key) is more robust:

```tsx
key={`${card.id}-${mode}`}
```

### IN-02: `check-dup-defs.ts` limits the inner subquery with `LIMIT 5` — investigation may miss duplicate definitions beyond the first 5

**File:** `scripts/check-dup-defs.ts:19`

**Issue:** The subquery that finds `card_definition_id` values with multiple Normal printings uses `LIMIT 5`. This means the outer query will only show detail rows for the first 5 duplicate definitions found. As a diagnostic script this is acceptable for interactive use, but the `LIMIT` is inside the `IN (...)` predicate, which is non-standard and some query planners may treat it unpredictably. More importantly, the presence of `LIMIT 5` means the script will silently truncate its own findings if there are more than 5 duplicate definitions — which is exactly the condition that would be most important to investigate fully.

**Fix:** Remove the `LIMIT 5` from the inner subquery, or move it to the outer `ORDER BY` clause:
```sql
-- Remove LIMIT 5 from:
SELECT card_definition_id
FROM card_printings
WHERE variant_type = 'Normal'
GROUP BY card_definition_id
HAVING COUNT(*) > 1
-- Add to outer query instead:
ORDER BY cd.id, cp.set_code, cp.collector_number
LIMIT 50
```

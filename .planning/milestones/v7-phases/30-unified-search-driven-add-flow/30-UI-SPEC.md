# Phase 30 — UI Design Contract

> Visual and interaction contract for the unified search-driven add flow on the Manage Binder page. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase does not introduce a new design system — it extends existing, already-shipped components (`ManageTradeCard`, `VariantTradeSheet`, `VariantCollectionSection`, `VariantTradeSection`) and removes two surfaces (`ManualWantsAddFlow` card, the owned-only "Add Cards to Binder" grid). All tokens below are the **existing project tokens**, restated here as the binding contract for this phase's new/changed UI so the checker and executor have a single source of truth without re-deriving them from `globals.css`.

## Layout Contract

- Keep the existing 2/3 + 1/3 grid (`grid grid-cols-1 lg:grid-cols-3 gap-8`) on `manage/page.tsx` (CONTEXT.md D-08).
- Left column (`lg:col-span-2`), top position (where "Add Cards to Binder" previously sat): single `Card` titled "Add Cards & Wants" containing the search input and results grid. Trade Profile card stays above it, unchanged. Trade Offerings grid stays below it, unchanged.
- Right column (`space-y-6`): Trade Profile is NOT here (it's already in the left column per current code) — right column keeps `ManageWantsList` only; the "Add Manual Want" `Card` is deleted entirely (its content is absorbed into the new unified flow).
- Results grid: `grid grid-cols-2 sm:grid-cols-3 lg:grid-cols-4 gap-4`, reusing `ManageTradeCard` exactly as rendered in the current "Add Cards to Binder" grid (art-tile, best-available art, name caption below).
- No results render below the search input until ≥2 characters are typed (BINDER-11) — the container that would hold the grid is simply absent, not an empty grid with a placeholder.

## Interaction Contract

- **Search gating (D-02):** minimum 2 characters before any fetch/results; 150ms debounce (matches Phase 24 catalog debounce feel); match on card name + subtitle, case-insensitive.
- **Data fetch (D-01):** triggered once, on the first keystroke that reaches 2+ characters — fetches `/api/cards/all` (full catalog) + `/api/collection/owned-cards` in parallel, then filters/merges client-side. Not re-fetched on subsequent keystrokes (only re-filtered).
- **Results cap (D-02):** display at most ~20 tiles; show the "Showing top 20 matches" note when the underlying match count exceeds the cap.
- **Tile click:** opens the right-side Sheet (extends `VariantTradeSheet`), same trigger pattern as the existing owned-grid tile click.
- **Sheet variant list (D-05):** shows every printing of the card — owned AND unowned (current `VariantTradeSheet` filters to `ownedCount > 0`; this phase removes that filter).
- **Per-variant row, two independent stepper controls (D-06, D-07):**
  - Trade quantity stepper: enabled only when `ownedCount > 0`. When `ownedCount === 0`, the stepper is disabled (not hidden) and the "You don't own this variant" reason renders inline next to it.
  - Want quantity stepper: always enabled, regardless of ownership, for every variant row.
  - Both steppers use the existing minus/input/plus row anatomy from `VariantCollectionSection` / `VariantTradeSection` (`w-28` label, `size="icon"` outline buttons, `w-16` centered number input) — visually identical controls, just two of them per variant instead of one.
- **Status text per row:** "Owned" / "Not owned" reflects collection state (existing `VariantCollectionSection` pattern, informational only — not part of this phase's writes); "Trading" / "Not trading" reflects trade quantity > 0 (existing `VariantTradeSection` pattern); a new "Wanted" / analogous indicator for want quantity > 0, styled identically (`text-primary font-bold` when active, `text-muted-foreground` when not).
- **Optimistic updates:** both stepper actions follow the existing optimistic-update-then-rollback-on-error pattern already used by `updateTradeQuantity` / `updateWantQuantity` in `manage/page.tsx` — no new pattern introduced.

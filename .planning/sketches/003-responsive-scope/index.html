B: One rule everywhere — controls always on the tile

The literal reading of "nothing hover-dependent": put a real, visible control on every tile at every breakpoint. Built here so the failure is visible rather than argued.

It fails on desktop worse than on mobile. At 9 columns inside a 704px container, a tile is ≈—px. A two-button control cannot be 44px there — the buttons above are 30px, already below the floor, and still cramped. Sketch 001 rejected this at 118px; desktop is tighter.

Trade-offs

  • Breaks the 44px rule at both breakpoints to make it fit.
  • Changes row geometry everywhere, so estimateSize (card-grid.tsx:80) must change and every row needs measuring.
  • Art shrinks at every breakpoint to make room for chrome — directly against "card art forward".
  • One rule, one codepath — the only thing it has going for it.

C: One model, two containers

The interaction contract is identical everywhere — tap selects, controls live off the tile. Only the container changes: a bottom bar where there's no room, the existing 320px sidebar where there is.

The sidebar already exists and is under-used. Today it shows stats and validation only (deck-sidebar.tsx). Hosting the selected-card controls costs no new screen real estate and no new component category — it's the same "off-tile control surface" the mobile bar provides.

Trade-offs

  • One interaction contract — the tile behaves identically at every width. The findings skill's global rules stay literally true.
  • Desktop tiles keep full art at ≈—px — no chrome competing for the smallest tiles in the app.
  • estimateSize stays valid at every breakpoint — nothing is added below the art.
  • Desktop loses hover-to-adjust. Mouse users gain a select step they don't strictly need. That's the real cost.
  • Hover could still be layered on desktop as an accelerator without changing the contract — but that reintroduces two paths, so it's a deliberate follow-up decision, not a freebie.

Click tiles in both frames. The rhythm should feel like the same product.

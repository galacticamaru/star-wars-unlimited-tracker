A: Port the binder sheet as-is

Three stacked sections — Collection, Trade, Want — exactly as variant-trade-sheet.tsx composes them today. Path of least resistance: the components already live in src/components/catalog/.

Open the drawer and change a Collection count on an unowned variant. The Trade section stays locked until a refresh lands. Each section holds its own useState seeded from props (variant-collection-section.tsx:22, variant-trade-section.tsx:25, variant-want-section.tsx:23) and Trade is gated on ownedCount — which Collection mutates locally without telling anyone.

Watch the counter bottom-left: each section fires its own router.refresh().

Trade-offs

  • Cheapest to build — the composition already exists and is proven in the binder.
  • Ships the known bug into the main surface. The pending todo becomes the thing users look at, not an edge case.
  • Three sections × N variants is a lot of vertical scroll for a card with 4 printings.
  • Redundant labels — the same variant name is repeated in all three sections.

B: One unified variant table

Rows are printings. Columns are Owned, Trade, Want. Each variant appears exactly once, and the three numbers that describe it sit side by side.

The coupling is fixed by construction. One row owns all three values for a printing, so there is one state object and no cross-section gate to go stale. Set Owned to 1 and the Trade cell in the same row unlocks immediately — no refresh, no callback threading.

Trade-offs

  • Densest — a 4-printing card fits without scrolling. A shows the same data at roughly 3× the height.
  • Kills the stale-gate class of bug rather than patching one instance.
  • Biggest rewrite. The three existing components stop being reusable as-is; their shared logic would need extracting into one row component.
  • Cells are 26px — below the 44px floor. Fine for a mouse, needs checking on the phone frame. This is a genuine risk, not a footnote.
  • Three numbers per row can read as busy. Judge whether the column headers carry it.

C: Ownership-first, progressive

Keeps the three sections but makes their dependency explicit and ordered. Collection is always there. Trade appears only once you own something and says so when you don't. Want is always available, since you can want a card you don't own.

The gate becomes visible rather than mysterious. Under A, a locked Trade section looks broken. Here it states its condition — and because the sections share one state object, setting an Owned count reveals Trade immediately.

Trade-offs

  • Preserves the existing components more than B does — same sections, shared state lifted up.
  • Teaches the model — the ownership rule that gates trading is stated in the UI instead of enforced silently.
  • Still tall. Less than A, more than B. A 4-printing card scrolls on the phone.
  • Sections appearing and disappearing causes layout shift as you edit. Watch whether that feels responsive or jumpy.

What differs

  • Container: bottom bar vs full-screen drawer.
  • Depth: selector edits one number (deck count). Catalog edits three per printing.
  • Dismissal: the bar is ambient and never blocks; the drawer is modal and must be closed.
  • Persistence: the bar stays warm across cards — tap another tile and it re-targets. The drawer closes and reopens.

What holds

  • Identical tiles, identical selection ring, identical corner ⓘ.
  • Tap selects, never navigates — in both.
  • Controls always off the tile — in both.
  • Nothing hover-dependent — in both.
The read: the contract is shared; only the container scales with the depth of the job. One number gets an ambient bar; twelve numbers get a modal drawer. That is arguably correct rather than inconsistent — but it is worth deciding deliberately, because a user moving between these two screens meets both within seconds.

The alternative

Force one container everywhere: a drawer in the deck builder too. Rejected in sketch 001 — a drawer per card while adding 50 cards is more taps, not fewer.
